# 「求真」V2.7 升级记录

**日期**：2026-08-30
**范围**：将插件从"密钥硬编码于 `generated-config.js`"迁移为"密钥仅存于云端、扩展零密钥"的安全可移植形态。引入 Cloudflare Workers 透明代理，彻底改变密钥持有与请求中转架构。

## 1. 阶段 A：Cloudflare Workers 透明代理

### 1.1 架构变化：从"密钥在前端"到"密钥在云端"

```
改造前（V2.6）：
  扩展 SW ──直连──▶ DeepSeek / 知乎 / metaso / Exa
             ↑
     generated-config.js 硬编码全部密钥
     （任何安装者解压即读走，无法撤销/限流）

改造后（V2.7）：
  扩展 SW ──HTTPS──▶ CF Worker (api.anota.best) ──▶ DeepSeek / 知乎 / metaso / Exa
             ↑                        ↑
     仅持访问令牌              真实密钥存 Worker Secrets
     （可撤销/轮换）           （永不下发前端）
```

### 1.2 关键设计决策

| 决策点 | 结论 | 理由 |
|---|---|---|
| 代理形态 | **透明代理**：响应结构与第三方原样一致 | 扩展端归一化/评分/验证逻辑零改动；`smoke-search-advise.js` 45 项断言直接当回归网 |
| 认证机制 | 阶段 A 用静态 `ACCESS_TOKEN`；阶段 3 换知乎 OAuth JWT | 先跑通链路，不被 OAuth 联调阻塞 |
| 密钥存储 | Cloudflare Workers Secrets | 加密存储，`wrangler secret put` 管理，不进代码仓库 |
| 域名 | `anota.best`，子域 `api.anota.best` | TLS 证书 + OAuth redirect_uri 的前提 |
| 回退机制 | 保留 DIRECT 模式（本地密钥） | 每步可独立回退，不影响开发调试 |

### 1.3 Worker 路由表

| 路由 | 上游 | 方法 | 认证注入 |
|---|---|---|---|
| `POST /v1/chat/completions` | `https://api.deepseek.com/chat/completions` | 透传 body | `Authorization: Bearer <DEEPSEEK_API_KEY>` |
| `GET /api/v1/content/zhihu_search` | `https://developer.zhihu.com/api/v1/content/zhihu_search` | 透传 query params | `Authorization: Bearer <ZHIHU_ACCESS_SECRET>` + `X-Request-Timestamp`（Worker 重新生成） |
| `GET /api/v1/content/global_search` | 同上 | 同上 | 同上 |
| `POST /metaso/search` | `https://metaso.cn/api/v1/search` | 透传 body | `Authorization: Bearer <METASO_API_KEY>` |
| `POST /exa/search` | `https://api.exa.ai/search` | 透传 body | `x-api-key: <EXA_API_KEY>` |
| `GET /health` | — | 探活 | 无需认证 |

### 1.4 部署配置

```toml
# wrangler.toml
name = "qiuzhen-proxy"
main = "worker.js"
compatibility_date = "2024-09-23"

[vars]
DEEPSEEK_BASE_URL = "https://api.deepseek.com"

  { pattern = "api.anota.best/*", zone_name = "anota.best" }
```

Secrets（`wrangler secret put`，共 5 个）：
`DEEPSEEK_API_KEY` / `ZHIHU_ACCESS_SECRET` / `METASO_API_KEY` / `EXA_API_KEY` / `ACCESS_TOKENS`

## 2. 阶段 B：配置生成器改造

### 2.1 `scripts/gen-config.js` 双模式

| 模式 | 触发条件 | 密钥行为 | 产物 |
|---|---|---|---|
| **PROXY** | 项目根存在 `proxy_base.txt` | **不读取任何本地密钥文件**，全部置 `null` | 仅含 `PROXY_ENABLED` / `PROXY_BASE_URL` / `PROXY_ACCESS_TOKEN` |
| **DIRECT** | 无 `proxy_base.txt` | 读取 `*_api.key`（原逻辑） | 含全部密钥（开发后门） |

### 2.2 新增输入文件（均 gitignored）

| 文件 | 内容 | 用途 |
|---|---|---|
| `proxy_base.txt` | `https://api.anota.best` | 代理地址；存在即启用 PROXY 模式 |
| `proxy_token.txt` | `<openssl rand -hex 32>` | 用户访问令牌 |

### 2.3 生成的 `generated-config.js` 结构

```javascript
// PROXY 模式产物（分发包使用）
globalThis.QIUZHEN_CONFIG = Object.freeze({
  PROXY_ENABLED: true,
  PROXY_BASE_URL: "https://api.anota.best",
  PROXY_ACCESS_TOKEN: "<用户访问令牌>",
  DEEPSEEK_API_KEY: null,          // ← 全部为 null，零密钥
  DEEPSEEK_BASE_URL: 'https://api.deepseek.com',
  DEEPSEEK_MODEL: 'deepseek-chat',
  ZHIHU_ACCESS_SECRET: null,
  ZHIHU_API_BASE: 'https://developer.zhihu.com/api/v1/content',
  METASO_API_KEY: null,
  METASO_ENDPOINT: 'https://metaso.cn/api/v1/search',
  EXA_API_KEY: null,
});
```

**关键保证**：代理模式下，`generated-config.js` 中所有第三方密钥字段为 `null`。扩展包中真正零密钥。

## 3. 阶段 C：扩展端全模块代理适配

### 3.1 统一改造模式

所有直连 DeepSeek 的模块，采用完全一致的三件套辅助函数（插在 `var CONFIG = ...` 之后）：

```javascript
function isProxy() { return !!(CONFIG && CONFIG.PROXY_ENABLED === true && CONFIG.PROXY_BASE_URL); }
function isLlmAvailable() { return isProxy() || !!(CONFIG && CONFIG.DEEPSEEK_API_KEY); }
function llmRequestParts() {
  if (isProxy()) {
    return { url: CONFIG.PROXY_BASE_URL + '/v1/chat/completions', auth: 'Bearer ' + CONFIG.PROXY_ACCESS_TOKEN };
  }
  return { url: CONFIG.DEEPSEEK_BASE_URL + '/chat/completions', auth: 'Bearer ' + CONFIG.DEEPSEEK_API_KEY };
}
```

每个模块的改动点固定为 3 处：
1. **辅助函数**（上述三件套）
2. **`callLLM` / `callDeepseek` / `callChunk` 的 `fetch`**：`CONFIG.DEEPSEEK_BASE_URL + '/chat/completions'` → `parts.url`；`'Bearer ' + CONFIG.DEEPSEEK_API_KEY` → `parts.auth`
3. **入口可用性校验**：`!CONFIG || !CONFIG.DEEPSEEK_API_KEY` → `!isLlmAvailable()`

### 3.2 逐文件改动清单

| 文件 | 调用函数 | 改动点 | 影响链路 |
|---|---|---|---|
| `datasource.js` | `apiGet`（知乎）/ `searchMetaso` / `searchExa` | 新增 `isProxy()`；三个请求函数 + 三个可用性函数 | 知乎站内/全网、metaso、Exa 检索 |
| `analyzer.js` | `callDeepseek` | 三件套 + `callDeepseek` fetch + `isConfigured` | 三模式分析（求真/求深/求异） |
| `claim-detector.js` | `callChunk` | 三件套 + `callChunk` fetch + `detectClaims` 入口 | 全文 Claim 识别 |
| `query-analyzer.js` | `callLLM` | 三件套 + `callLLM` fetch + `analyzeQuery` 入口 | 搜索策略判定 |
| `source-analyzer.js` | `callLLM` | 三件套 + `callLLM` fetch + `analyzeSource` 可用性判断 | 来源画像分析 |
| `verify-engine.js` | `callLLM` | 三件套 + `callLLM` fetch + `verifyClaim` 入口 | 五态验证 + 求异 |
| `evidence-target.js` | `callLLM` | 三件套 + `callLLM` fetch + `analyze` 入口 | 证据目标分析 |

### 3.3 `datasource.js` 的特殊处理

`datasource.js` 不走 `llmRequestParts()`（它不调 DeepSeek），而是对三个数据源分别处理：

| 数据源 | 代理模式 URL | 代理模式认证头 | 直连模式（不变） |
|---|---|---|---|
| 知乎 | `PROXY_BASE_URL + '/api/v1/content' + path` | `Bearer PROXY_ACCESS_TOKEN` | `ZHIHU_API_BASE + path` + `Bearer ZHIHU_ACCESS_SECRET` + `X-Request-Timestamp` |
| metaso | `PROXY_BASE_URL + '/metaso/search'` | `Bearer PROXY_ACCESS_TOKEN` | `METASO_ENDPOINT` + `Bearer METASO_API_KEY` |
| Exa | `PROXY_BASE_URL + '/exa/search'` | `Bearer PROXY_ACCESS_TOKEN` | `api.exa.ai/search` + `x-api-key: EXA_API_KEY` |

可用性判断统一改为：`isProxy() || !!(CONFIG && CONFIG.<对应密钥>)`

### 3.4 零改动确认依据

| 文件 | 不调 DeepSeek 的原因 |
|---|---|
| `v25-pipeline.js` | 纯编排层，通过 `QA.analyzeQuery` / `SA.analyzeSources` 等间接调用（底层已改） |
| `provenance.js` | 上游线索提取是正则规则；`trace()` 走 `READER.readUrl` + `DS.engineSearch`（已改造的 datasource） |

## 5. 行为变化汇总

| 场景 | V2.6（改造前） | V2.7（改造后） |
|---|---|---|
| 密钥位置 | `generated-config.js` 明文硬编码，随扩展包分发 | 仅存于 Cloudflare Worker Secrets，扩展包零密钥 |
| 密钥泄露风险 | 任何安装者解压即读走全部密钥 | 扩展仅持访问令牌，泄露可随时在 Worker 端撤销/轮换 |
| 请求路径 | 扩展 → 直连第三方 | 扩展 → CF Worker（认证 + 注入密钥）→ 第三方 |
| 响应结构 | 第三方原始响应 | **不变**（透明代理），下游归一化/评分/验证零改动 |
| 可用性判断 | 检查本地密钥是否存在 | `isProxy() \|\| 本地密钥存在`（代理模式视为可用） |
| 分发可行性 | 不可分发（密钥暴露） | 可安全分发（零密钥 + 令牌可撤销） |
| 回退能力 | — | 删除 `proxy_base.txt` → 重跑 `gen-config.js` → 回到 DIRECT 模式 |
| 知乎时间戳 | 扩展端生成 `X-Request-Timestamp` | Worker 重新生成（扩展端不再需要） |
| 限流/审计 | 无 | Worker 端可按令牌做限流/用量统计（待实施） |
